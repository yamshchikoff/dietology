## Протокол обсуждения требований

### 2026-05-19 — Стартовые требования

Разрабатываем персонального ассистента по питанию.

Ассистент должен хранить в удобном для пользователя и LLM виде:

1. **Историю диалога** — полный лог общения пользователя с ассистентом.
2. **Нетривиальные находки** — insights, обнаруженные в ходе анализа питания: закономерности, корреляции, аномалии, точки роста.
3. **Антропометрические и медицинские параметры** пользователя — вес, рост, возраст, пол, лабораторные показатели, аллергии, хронические состояния и т.д.

Формат хранения должен быть одинаково пригоден для чтения человеком и для подачи в контекст LLM.

### 2026-05-19 — Платформенные требования

**MVP:** нативное кроссплатформенное приложение под Windows и Linux, с веб-интерфейсом.

**Дальнейшие версии:** Android, iPhone.

**Архитектурное требование:** ядро (core) должно быть платформонезависимым. UI-слой — веб-технологии, обёрнутые в нативный контейнер. Закладываем разделение на core/UI с первого дня, чтобы добавление новых платформ не требовало переписывания логики.

### 2026-05-19 — Среда разработки и тестирования Windows

Разработка ведётся на Linux. Тестирование нативных Windows-сборок требуется отложить без блокировки разработки. Рассматриваем:

- **Эмуляция (Wine)** — предпочтительный вариант, легковесный, не требует виртуальной машины.
- **Виртуализация (VM)** — запасной вариант, если Wine не покроет нужд.

Требуется определить конкретный инструмент и зафиксировать процедуру Windows-тестирования.

### 2026-05-19 — Кроссплатформенная архитектура (Tauri)

В качестве нативного кроссплатформенного фреймворка выбран **Tauri v2**:

- **Rust-ядро** — вся бизнес-логика, хранение данных, работа с LLM.
- **Web UI** — HTML/CSS/JS, единый для всех платформ.
- **IPC-мостик** — связь Rust ↔ WebView через Tauri API.

Платформы из одной кодовой базы:

| Платформа    | Формат сборки      | WebView            | Rust-таргет   |
|-------------|-------------------|--------------------|---------------|
| Windows     | `.exe` / `.msi`   | WebView2 (Edge)    | x86_64-pc-windows-msvc |
| Linux       | AppImage / `.deb` | WebKitGTK          | x86_64-unknown-linux-gnu |
| Android     | `.apk` / `.aab`   | Android WebView    | aarch64-linux-android |
| iOS         | `.ipa`            | WKWebView          | aarch64-apple-ios |
| Web         | статика           | любой браузер       | — (wasm при необходимости) |

**Android:** Rust компилируется в нативный `.so` (ARM/x86) через NDK. Java/Kotlin-прослойка минимальна, генерируется Tauri. Ручной Java-код не требуется.

**iOS:** Rust компилируется в ARM64. Swift/ObjC-прослойка минимальна, генерируется Tauri. WKWebView — системный, тот же что Safari.

**Общий принцип:** ядро пишется один раз на Rust. UI пишется один раз на веб-технологиях. Добавление новой платформы = конфигурация Tauri-таргета, без переписывания логики или интерфейса.

### 2026-05-19 — Экспорт и импорт данных

**Формат хранения и обмена:** JSON-подобный структурированный формат. Markdown и прочие человекочитаемые форматы — не цель для внутреннего представления.

**Человекочитаемость экспорта/импорта — no-goal.** Если в будущем потребуются человекочитаемые экспорты — они разрабатываются как отдельная функция, дополнительными экспортными форматами.

**Импорт:**
- Все внешние данные проходят предобработку через LLM на входе.
- Исследования в неродных форматах (PDF-выписки, таблицы из клиник, сканы анализов) транслируются в родной JSON-подобный формат перед сохранением. Никакие «сырые» чужеродные форматы не хранятся.

**Экспорт — две опции:**
1. **Частичный:** экспорт отдельного исследования или другой части истории в JSON-формате.
2. **Полный:** экспорт всего внутреннего состояния (вся история, все находки, все параметры) в JSON-формате.

### 2026-05-19 — Этические принципы проекта

1. **Безусловный приоритет пользователя.** Приложение и ассистент служат своему пользователю. Благо пользователя — неотменяемый и безусловный приоритет любых рекомендаций. Интересы иных лиц или организаций не учитываются при формировании рекомендаций.

2. **Область компетенции — хороший врач-диетолог с компетенциями врача общей практики.**
   - Ассистент работает как экспертная система по диетологии и, в общем смысле, над физическим и духовным благополучием пользователя.
   - Он вправе давать рекомендации по несложным случаям в рамках компетенции диетолога и GP.
   - При подозрении на сложный случай (в том числе диетологический) — ассистент обязан настоятельно рекомендовать обратиться к соответствующему врачу.
   - Не преуменьшать угрозу. Не преувеличивать угрозу. Сообщать ровно то, что известно.

3. **Границы компетентности.** Приложение не должно в разумных пределах нарушать границы своей компетентности. Что за пределами — к тому ассистент не должен давать рекомендаций, но должен направить к специалисту.

4. **Не создавать зависимость.** Мы не создаём систему, которая привязывает к себе пользователя и вызывает необоснованную зависимость от инструмента.

5. **Не преуменьшать пользу.** Мы не преуменьшаем необоснованно благо, которое система способна создать для пользователя. Если система может помочь — она должна это сделать.

### 2026-05-19 — Принцип герметичности

**Production-ready система должна иметь выход в интернет только на эндпоинт инференса LLM.** Никаких иных внешних соединений.

**Модель угрозы — prompt injection.** Инференс-эндпоинт не должен иметь возможности поиска в интернете или скачивания страниц. Никакой инструментальный доступ к сети со стороны LLM.

**Полезная внешняя информация** (справочники, базы знаний, исследования) — может быть включена в систему одним из двух путей:

1. **Плагины** — изолированные модули, добавляющие знания или функциональность без выхода в сеть на инференсе.
2. **Версионирование данных** — обновления базы знаний через релизы приложения (не через runtime-доступ к интернету).

### 2026-05-19 — Принцип обязательной аннотации данных

Все данные, поступающие во внутренний контур системы, маркируются обязательными метаданными. Расхождение между системными и предполагаемыми атрибутами **не является конфликтом** — это сосуществующие слои: что система знает точно и что заявляет источник.

**Обязательные системные атрибуты (ground truth):**

1. **Системная дата и время поступления** — когда данные попали в систему. Отвязана от даты создания исходного документа. Это системный лог.
2. **Внутрисистемное авторство** — кто создал данные внутри системы: `agent` или `user`.

**Обязательные атрибуты источника (claims из документа):**

3. **Предполагаемая дата создания** оригинального документа — что заявляет сам документ о своей дате.
4. **Предполагаемое авторство** оригинального документа — что заявляет документ о своём авторе (лаборатория, врач, клиника).

Пример: пользователь загружает анализ крови, в котором написано «15.03.2026, лаборатория Инвитро». Система фиксирует: поступило `2026-05-19T14:31:00Z`, автор `user`, предполагаемая дата `2026-03-15`, предполагаемый автор `Инвитро`. Мы не можем знать, действительно ли документ создан тогда и там, но сохраняем эти утверждения.

### 2026-05-19 — Принцип персистентности и версионирования данных

**Данные не переписываются.** Если необходима редактура, создаётся новая версия документа, обоюдно слинкованная с предыдущей, с короткой аннотацией причины создания новой версии.

**Приоритет версий — предельно чёткий:**
- Валидна только выбранная (активная) версия документа.
- При базовых операциях LLM в контекст попадает только активная версия.
- В контексте видны только ссылки на другие версии и причины версионирования (защита от замусоривания неактуальными данными).
- Предыдущие версии агент может прочитать явно и отдельно, с согласия пользователя.

**Удаление версии (исключение из принципа неизменности):**
- Удаляется конкретная версия в цепочке (не обязательно весь документ).
- Только по инициативе пользователя.
- С проверкой на осознанность операции.
- Пользователю показывается: какие версии удаляются и какая версия станет активной после удаления.
- Юзкейс: ошибочно загружен чужой анализ — безвозвратное удаление, от такой версии только угроза, пользы нет.

**Режим расследования (отдельный юзкейс):**
- Модель может сама запросить переход в режим расследования, но пользователь должен **явно подтвердить** вход в него.
- В режиме расследования модель получает автоматический доступ ко всем версиям всех документов — может сама запрашивать помещение нужных версий в контекст.
- Пользователю **чётко и недвусмысленно** видно, что модель находится в режиме расследования.
- В режиме расследования модель **ничего не удаляет и не меняет** — только читает и порождает артефакты расследования.
- В режиме расследования модель **не порождает ничего, кроме артефактов расследования**. Это единственный и формальный гейт выхода из режима: расследование завершено, когда порождены артефакты.
- В режиме расследования модель может общаться с пользователем. Эта история диалога подчиняется общим правилам аннотации и становится частью артефактов расследования.
- **Артефакты расследования** — model-initiated документ с обязательной аннотацией (системная дата, авторство `agent`, ссылки на исследованные версии, причина создания), встраиваемый в общее состояние системы. Включают в себя историю диалога в режиме расследования.

### 2026-05-19 — No-goals

Система **не является**:

1. **Базой данных.** Не предполагает полноценной db-функциональности.
2. **Браузером.**
3. **Агентом общего назначения.**
4. **Операционной системой.** Не должна претендовать на развитие OS-подобного функционала в ущерб своему назначению.
5. **Предельно гибкой разработкой.** Гибкость не должна достигаться в ущерб удобству применения по назначению и в ущерб основным целям.

### 2026-05-19 — Основная задача персистентного хранилища

Внутреннее персистентное хранилище — **эффективная долговременная память модели**. Работа ведётся по двум направлениям, образующим основное диалектическое противоречие проекта:

1. **Полнота доступа.** Модель должна быть в состоянии получить любую информацию из истории переписки и из исследований — вовремя, в нужном объёме, в комбинации с нужным количеством другой связанной информации.

2. **Освобождение контекста.** Модель должна быть в состоянии освободить контекст от нерелевантной информации.

Это противоречие (полнота vs. релевантность) — не баг, а диалектический движущий принцип развития проекта.

### 2026-05-19 — Нетривиальные находки (insights)

Работа агента предполагает выявление нетривиальных находок — инсайтов, которые напрямую не следуют из корпуса исследований, но являются важными для пользователя.

**Требование к размещению:** находки должны располагаться в структурно выделенном, всегда легко достижимом месте — так, чтобы модель всегда «имела в виду», что у неё в памяти есть важные сведения, не выводимые напрямую из сырых данных. Находки не должны тонуть в истории диалога.

### 2026-05-19 — LLM-провайдер

Приводом модели служит **DeepSeek API, совместимый с протоколом Anthropic API**. Разработка ведётся с учётом технической документации DeepSeek на Anthropic API.

### 2026-05-19 — Модель хранения: директория как структура, git как версионирование

**Не монолитный JSON, а дерево директорий с отдельными файлами.** Каждый документ — отдельный `.json`. Версия — отдельный файл. Git даёт версионирование бесплатно.

```
data/
├── history/
│   └── 2026-05-19.jsonl    # диалог за день/сессию, одна реплика = одна строка (append-only)
├── topics/
│   └── topics.json          # реестр тем → указатели на дни/реплики в history
├── findings/
│   └── low-iron-pattern/    # директория находки
│       ├── v1.json
│       └── v2.json
├── parameters/
│   └── blood-test-2026-03/  # директория исследования
│       ├── v1.json
│       └── v2.json
└── meta.json                # указатели: активные версии, режим, ссылки
```

**Диалог — JSON Lines (`.jsonl`), а не поштучные JSON:**
- Одна реплика = одна строка, добавление атомарно (append-only).
- День/сессия — естественная граница: старые дни стабильны, текущий день активен.
- Git коммитит дифф дописанных строк, история не распухает.

**Topics — лёгкий индекс над историей:**

| | Topics | Findings |
|---|---|---|
| Что | О чём говорили | Что обнаружили |
| Роль | Индекс, навигация | Знание, инсайт |
| Источник | Извлекается из диалога | Выводится из анализа |
| Жизненный цикл | Обновляется с каждым днём | Живёт пока актуален |

Модель при входе в контекст видит реестр тем, а не всю историю. Запрос пользователя → модель смотрит topics → открывает нужные дни.

**Версионирование документов через git, не через commit-линковку:**
- Версия документа монотонно растёт (v1 → v2 → v3), прописана и в JSON-файле, и в commit message.
- Линковка из диалога на документ идёт по номеру версии, а не по хешу коммита. Хеш коммита нестабилен при переписывании истории.
- **Удаление — только перекрывающий коммит**, не удаление коммита. Если ошибочно загруженный документ нужно убрать: коммит с удалением файла и причиной в commit message. Версионная последовательность сохраняется, номер версии не переиспользуется.
- При линковке на версию из диалога — рядом ставится ссылка на актуальную версию с пометкой «справочно: актуальная версия — vN, исторически обсуждалась vM».
- Контролирует версии git, а не ручная линковка. Риск замусоривания контекста нерелевантным документом невелик — git хранит всё, модель читает только активную версию.

### 2026-05-19 — Архитектура MVVM

Проект принимает **MVVM** как архитектурный паттерн:

- **Model** — Rust-ядро: данные, LLM-взаимодействие, версионирование, хранение.
- **ViewModel** — Rust-слой между Model и View: подготовка данных для отображения, валидация, форматы (включая формат визуализации).
- **View** — Web UI (HTML/CSS/JS в Tauri WebView): рендерит данные от ViewModel, не содержит бизнес-логики.

### 2026-05-19 — Визуализация динамики показателей

Модель должна уметь генерировать JSON-описание визуализации динамики характеристики во времени.

- **Формат визуализации** — определённый JSON-схемой, понятной ViewModel. Модель осведомлена о схеме и умеет интерпретировать диагностику ViewModel (ошибки валидации формата).
- **View** — робастно отображает разумно широкий набор графиков (линейные, столбчатые, множественные ряды, наложение нормативных диапазонов).
- **Подбор или разработка view-компонента** — требуется выбрать готовую библиотеку (например, ECharts, Chart.js, Vega-Lite) или разработать специализированный компонент, адекватный медицинской визуализации.

### 2026-05-19 — Управление контекстом: Ethics First и housekeeping

**Ethics first.** Каждый контекст модели должен включать полный этический кодекс и назначение системы (см. «Этические принципы проекта»). При перезапуске контекста этический кодекс загружается первым — до любых данных пользователя. Сразу после этического блока инжектится верхняя часть карты доступа (до порога загрузки, определённого в разделе «Модель пользователя и карта доступа»).

**Мониторинг заполнения контекстного окна.** Модель обязана следить за наполнением контекста и при приближении к лимиту выполнять housekeeping:

1. **Выявлять нетривиальные findings** — извлечение инсайтов из текущего контекста и сохранение в `findings/` до того, как контекст будет очищен.
2. **Конспектировать topics** — обновление реестра тем в `topics/topics.json`: что обсуждалось, в каких днях, ключевые выводы.
3. **Пополнять карту (user-map)** — обновление карты доступа пользователя: пересборка приоритетов, фиксация новых находок, обновление тем (детально специфицировано в разделе «Модель пользователя и карта доступа»).

Цель: при перезапуске контекста модель теряет оперативную память, но не знания. Всё нетривиальное должно быть сохранено в персистентном хранилище до очистки контекста.

### 2026-05-19 — Версионирование формата экспорта/импорта

**Принцип 1:1.** Версия приложения = мажорная версия формата. Минорная версия — для обратно-совместимых расширений внутри мажорной.

**Совместимость:** приложение принимает все предыдущие мажорные версии формата, включая текущую.

**Расширяемость:** формат разрабатывается так, что расширения не ломают его — неизвестные ключи игнорируются, а не вызывают отказ. Минорная версия повышается при добавлении новых полей, мажорная — при ломающих обратную совместимость изменениях.

### 2026-05-19 — Single-user архитектура

Приложение обслуживает **одного пользователя** на одну инсталляцию. Не семейный, не многопользовательский режим. Структура `data/` и карта рассчитаны на одного пользователя.

### 2026-05-19 — Шифрование данных на диске

В прототипе — нет. Оставляется как future consideration.

### 2026-05-19 — Модель пользователя и карта доступа

Диалог + находки + исследования не могут быть «моделью пользователя» напрямую — при первой же очистке контекста модель теряет к ним доступ. Нужна **карта доступа** — компактное представление, которое всегда помещается в контекст и указывает модели, что важно и куда смотреть.

**Три слоя работы с данными:**

1. **Данные** (`data/`) — сырой материал: история, исследования, находки. Персистентно, версионировано.
2. **Карта доступа** — компактный слой, всегда в контексте. Не сами данные, а указатели. По духу ближе к тому, как врач помнит пациента: ключевые факты, риски, динамика, не все анализы наизусть.
3. **Активный контекст** — карта + релевантные данные, подгруженные из хранилища под текущую задачу.

**Состав карты доступа:**
- Базовые параметры пользователя (возраст, пол, вес, рост) — всегда в контексте.
- Ключевые находки с пометкой важности.
- Активные темы (что беспокоит сейчас).
- Хронологический силуэт — значимые вехи, не все дни.

**Жизненный цикл карты:**
- Создаётся при первом запуске: модель проводит вводное интервью и собирает базовую карту (конкретная методология — отдельный методический вопрос, фиксируется позже).
- Обновляется моделью при housekeeping (обязательно).
- Может дополняться моделью в ходе диалога (при существенных обнаружениях).

**Скоуп карты — одна на пользователя.** Это буквально всё, что один человек знает о другом: не только медицина и диетология, но и особенности ведения беседы, темы которые раздражают, предпочтения в общении, психологический профиль. Холистическая модель пользователя.

**Формат хранения карты — монолитный JSON под контролем git.**
- Один файл `data/user-map.json`.
- Каждый пасс (housekeeping, дополнение в диалоге) коммитится. Монолитность сохраняется, защита от повреждений через git.
- Если модель считает, что нужно картировать — командует картирование через тулинг, программа делает изменение и коммитит. Каждое изменение под git.

**Структура карты — самобалансирующееся дерево с корневой нодой.**
- Карта сама по себе может быть графом с циклами (связи между темами, находками, параметрами).
- Но «верх» карты определяется по корневой ноде, за которую подвешен граф. Приоритет доступа = расстояние от корня.
- Верхняя часть карты разумно ограничена по размеру.
- Если карта шире порога — верхняя часть содержит достаточное число линков по каждому расширенному топику на ту часть карты, что не грузится сразу в контекст. Двухуровневая загрузка: верх всегда в контексте, остальное — по ссылкам.

**Гранулярность карты:** важность, срочность, теги — структурно, не flat.

**Корневая нода — фиксированная.** Это root модели пользователя, не переопределяется динамически. Структура дерева от корня стабильна, перебалансировка меняет приоритеты ветвей, а не сам корень.

**Метрика и триггер самобалансировки.** Перебалансировка происходит на каждом перезапуске контекста. При балансировке:
- Высокая представленность recent (недавнее).
- Важное из прошлого сохраняется независимо от давности.
- Важное для гладкой коммуникации (особенности общения, триггеры, предпочтения) всегда представлено.
- При ребалансировке может проводиться фактологическая сверка с topics и findings.

**Отношения карты с topics и findings.** Карта дублирует ключевые поля из `topics/` и `findings/`. Если поля помещаются под порог — дублирует всё. Если нет — ссылается. Модель не должна ходить по ссылкам за тем, что обязана знать сразу (аналогия: что человек помнит о другом человеке, не заглядывая в записи).

**Права пользователя на карту.** Карта — private encapsulated property модели на функциональном уровне. Пользователь может что угодно сказать в диалоге, но вносить ли изменения в карту — решает модель. При этом:
- Карта не защищается принципиально от пользовательской редактуры (формально это собственность пользователя).
- Карта сериализуется в экспортный JSON наравне со всем состоянием.
- UI-доступ к карте не предусмотрен.

**Верификация карты при загрузке контекста.** Карта хранит ссылки на коммиты топиков, findings и исследований, на которых она основана. При загрузке работает формальный детектор потенциальных расхождений: если целевые данные изменились (новый коммит) после последнего обновления карты — модель получает флаг о расхождении и решает, нужно ли перечитывать.

**Политика забывания.** Информация низкой важности, долго не запрашивавшаяся и не критическая для гладкой коммуникации, может вытесняться вниз от корневой ноды — оставаясь в карте, но ниже порога загрузки. Однако есть данные, которые **не могут быть удалены или вытеснены** из активной части карты, даже если пользователь этого желает: угрожающие жизни состояния, критические противопоказания, аллергии, зависимости. Карта служит благу пользователя, а не его комфорту — это прямое следствие этических принципов проекта.

**Карта и метод её ведения — основной актив проекта.** Именно это отличает систему от бесплатного чата: не одноразовый диалог, а накапливаемая, структурированная, этическая память о пользователе во времени. Карта — не вспомогательный инструмент, а ядро ценности системы.

### 2026-05-19 — Тулинг модели (Model Tooling API)

Модель работает через Anthropic-compatible tool use. Rust-ядро предоставляет функции, модель вызывает их. Каждый пишущий тул завершается автоматическим git commit.

**Чтение данных:**

| Тул | Аргументы | Назначение |
|-----|-----------|------------|
| `read_history` | `date` | День диалога (JSONL) |
| `list_topics` | — | Реестр тем |
| `list_findings` | — | Список находок с метаданными |
| `read_finding` | `name`, `?version` | Конкретная находка (по умолчанию — активная версия) |
| `list_parameters` | — | Список исследований |
| `read_parameter` | `name`, `?version` | Конкретное исследование |
| `read_user_map` | — | Полная карта пользователя |
| `read_user_map_field` | `key` | Поле карты по ссылке-ключу |
| `list_versions` | `name` | Все версии документа |
| `check_discrepancies` | — | Сравнить коммиты карты с HEAD данных |

**Запись данных (каждый вызов → git commit):**

| Тул | Аргументы | Назначение |
|-----|-----------|------------|
| `update_user_map` | `diff`, `reason` | Изменить/добавить/удалить поле карты |
| `update_topics` | `changes`, `reason` | Обновление реестра тем |
| `update_meta` | `changes`, `reason` | Обновление meta.json |
| `create_finding` | `name`, `content` | Новый insight |
| `update_finding` | `name`, `reason`, `content` | Новая версия находки |
| `annotate_entry` | `entry_id`, `presumed_date`, `presumed_author` | Проставить claims источника на запись |

**Расследование:**

| Тул | Аргументы | Назначение |
|-----|-----------|------------|
| `request_investigation` | `reason` | Запрос входа в режим расследования (пользователь подтверждает) |
| `load_version` | `name`, `version` | Загрузить не-активную версию в контекст (только в режиме расследования) |

**Вне тулинга (ядро делает само, без вызова модели):**
- Запись реплик диалога в JSONL.
- git commit после каждого пишущего тула.
- Удаление версий — только через UI, инициатива пользователя.
- Экспорт/импорт — UI.

**Импорт — часть общего диалога.** Пользователь приносит документ в ходе разговора («вот, посмотрите ещё это»). Модель читает, вызывает тулы для аннотирования (`annotate_entry`), сохранения, и далее — контекстно-зависимые действия: ответ пользователю, обновление карты, топиков, находок, меты — всё, что сочтёт нужным. Импорт не изолирован, это естественный поток диалога.
