> Харнесс: Claude Code (claude.ai/code). Модель: DeepSeek.
> Ведение проекта: каждая завершённая задача — отдельный коммит с push в оба remote.

## Контекст

**Стек:** Tauri v2 (Rust-ядро + Web UI HTML/CSS/JS). MVVM-архитектура.

**Текущее состояние:** реализован `ChatSession` с `Vec<Message>` и save/load в JSONL. Ни master description, ни findings, ни facts не реализованы. Автосохранение истории не подключено.

**Архитектура памяти** специфицирована в [requirements-discussion.md](./requirements-discussion.md), секции:
- 2026-05-19 — Основная задача персистентного хранилища
- 2026-06-03 — Базовые риски подсистемы памяти (риски 1–5)
- 2026-06-03 — Неизменяемость находок и структурная актуализация
- 2026-06-04 — Трёхуровневая архитектура памяти
- 2026-05-19 — Атомарная запись и валидация (в секции «Тулинг модели»)

**Эволюция user-map: отказ от древовидной структуры (2026-06-05).** User-map = вся memory-подсистема (Master Description + Facts + Findings + Conversational Preferences). Вместо сложного дерева с метриками важности и автоматической балансировкой — тупые пагинируемые тулы обхода facts и findings + жирное master-описание, переписываемое моделью через субагента за один пасс. Модель не гадает о глубине обхода: facts и findings доступны все, без структурных ограничений, через честную пагинацию. Детали — в секции Master Description и Фазе 5.

## Принципы реализации

1. **Ядро обслуживает инварианты, модель — содержание.** Каждый тул = enforcement point. Модель не может нарушить структурный инвариант.
2. **Один тул — одна операция.** Никаких комбо-операций.
3. **Read возвращает summaries; full content — по запросу.** Индексные запросы возвращают лёгкие структуры с ID, заголовком, статусом и флагами.
4. **Все write — через atomic rename + git commit.** Без исключений.
5. **Модель не пишет JSON.** Только семантические параметры тулов. Сериализация — responsibility ядра.
6. **Честная пагинация, без гадания.** `list_facts` и `list_findings` — тупые tools с offset/limit. Модель знает: facts и findings столько, сколько есть, ни больше ни меньше. Никаких структурных ограничений глубины, никаких неявных фильтров. Модель сама решает, сколько страниц просмотреть.
7. **Master-описание — всегда в контексте.** Единственный документ, переписываемый моделью через субагента за один пасс (загрузить master → все facts → все findings → проверить консистентность → переписать). Это навигационный слой, заменяющий раннюю древовидную модель user-map.

## Модель данных

### Facts

#### Imported Facts (импортированные медицинские данные)

Лабораторные исследования, анализы, выписки, заключения врачей. Попадают в систему через pipeline импорта, а не через тулинг модели. Модель только читает.

Структура директории (идентична user-reported facts):

```
data/facts/imported/<fact_id>/
├── v1.json
├── v2.json
└── versions.json  # индекс версий: [{version, created_at, reason}]
```

Minimal schema `v1.json` (поля `content` и `source` уточняются при реализации импорт-пайплайна):

```json
{
  "id": "ifact-<uuid>",
  "type": "imported",
  "version": 1,
  "created_at": "<системная дата поступления, RFC 3339>",
  "author": "user",
  "presumed_date": "<ISO 8601 или null — дата, заявленная в документе>",
  "presumed_author": "<строка или null — лаборатория, врач, клиника, заявленные в документе>",
  "content": {},
  "source": {},
  "findings": []
}
```

4 обязательных атрибута аннотации фиксируются сейчас:
- `created_at` — системная дата поступления (ground truth).
- `author` — `"user"` для всех imported facts (пользователь загрузил документ).
- `presumed_date` — дата, заявленная в исходном документе (claim источника).
- `presumed_author` — автор, заявленный в исходном документе (claim источника).

Поля `content` и `source` — структура уточняется при реализации импорт-пайплайна. `findings` — обратные ссылки, управляются ядром.

#### User-Reported Facts (сведения со слов пользователя)

Заполняются моделью через `create_user_reported_fact`. Один факт ≤ 1024 токена.

Структура:

```
data/facts/user-reported/<fact_id>/
├── v1.json    # первоначальная версия
├── v2.json    # исправленная версия (после correct_user_reported_fact)
└── versions.json  # индекс версий: [{version, created_at, reason}]
```

Поле `v1.json`:

```json
{
  "id": "urfact-<uuid>",
  "type": "user_reported",
  "version": 1,
  "created_at": "<системная дата — когда данные попали в систему, RFC 3339>",
  "author": "agent",
  "presumed_date": "<ISO 8601 или null — предполагаемая дата события со слов пользователя>",
  "presumed_author": "user",
  "content": "<текст модели, ≤1024 токена>",
  "disclaimer": "Данный факт сообщён пользователем в диалоге <ДАТА ФИКСАЦИИ>. Это дата фиксации сообщения моделью, а не время обсуждаемого события. Данный факт является суждением пользователя и получен в диалоге с ним — он может быть передан неточно, ошибочно или ложно. Загруженные в систему медицинские исследования обладают безусловным приоритетом над данным фактом. При выявлении расхождений с импортированными исследованиями причину расхождения следует выяснить в разговоре с пользователем и отметить отдельным суждением в разделе findings.",
  "findings": ["finding-<id1>", "finding-<id2>"]
}
```

Поля аннотации (принцип обязательной аннотации данных, 4 атрибута):
- `created_at` — системная дата поступления (ground truth). Подставляется ядром.
- `author` — внутрисистемное авторство: `agent` (факт зафиксирован моделью).
- `presumed_date` — предполагаемая дата события со слов пользователя (claim источника). Модель заполняет при создании, если пользователь указал временной контекст. Может быть `null`.
- `presumed_author` — `"user"` для всех user-reported facts (claim источника: пользователь сообщает о себе).

Поле `disclaimer` — обязательное, вставляется ядром, модель его не контролирует и не может убрать. Дата фиксации подставляется ядром при создании.

Поле `findings` — обратные ссылки на findings, управляются ядром при создании finding.

### Findings (заключения, инсайты)

Один finding ≤ 1024 токена. Неизменяем. Актуализация — только новый finding с новым ID (а не новая версия в той же директории).

```
data/findings/<finding_id>/
└── finding.json
```

Каждый finding — отдельная директория с единственным файлом. Никаких версий, никаких цепочек `prev`. Finding, однажды записанный, never touched.

Структура `finding.json`:

```json
{
  "id": "finding-<uuid>",
  "created_at": "<системная дата>",
  "author": "agent",
  "status": "active",
  "foundation_changed": false,
  "based_on": ["urfact-<id1>", "ifact-<id2>"],
  "content": "<текст finding, ≤1024 токена>",
  "reason": "<причина создания, контекст>"
}
```

Поля:
- `status`: `active` | `superseded`. Superseded — finding помечен неактуальным. Содержимое не трогается.
- `foundation_changed`: устанавливается ядром при вызове `correct_user_reported_fact` для всех findings, ссылающихся на исправленный факт. Сбрасывается только через `resolve_finding_status(reaffirmed)`.
- `based_on`: machine-readable ссылки на факты (urfact-* и ifact-*). Заполняется моделью при создании finding. Ядро валидирует существование всех ссылок.
- `content`: неизменяемый текст finding. Не дельта, не версия — полное содержание.
- `reason`: почему создан finding — контекст создания, а не версионирования.

Актуализация finding происходит не через создание v2 в той же директории, а через создание **нового finding с новым ID**, ссылающегося на актуальный набор фактов. Старый finding при необходимости помечается `superseded` через `resolve_finding_status`.

**Разрешение противоречия с ранней моделью delta-цепочек.** Секция требований от 2026-06-03 описывает версионирование findings через цепочки `prev` с инкрементальными `delta` (v1 → v2 → v3, полное содержание = сумма delta). Финальная архитектура от 2026-06-04 отказывается от этой модели в пользу **нулевой косвенности**: findings не связываются с другими findings, каждый finding — функция только от фактов, каждый содержит полный `content`, а не delta. Это устраняет риск штабелирования (Риск 4) структурно: глубина от факта до вывода всегда равна 1, модель не может создать неограниченно глубокую цепочку findings. Данный план реализует модель 2026-06-04.

### Master Description (мастер-описание)

Единственная сущность верхнего уровня, объединяющая целостную картину здоровья и навигационное оглавление памяти. Навигационный слой user-map. Заменяет первоначальную древовидную модель. ≤ 50 000 токенов. Модель переписывает целиком.

```
data/master-description/
├── v1.json      # все версии (v1, v2, v3...)
├── v2.json
└── active.json  # указатель + флаг
```

`active.json`:

```json
{
  "active_version": 2,
  "active_file": "v2.json",
  "foundation_changed": false
}
```

Версия мастер-описания:

```json
{
  "version": 2,
  "created_at": "<системная дата>",
  "content": "<текст модели, ≤50000 токенов>",
  "based_on_facts": ["urfact-<id>", "ifact-<id>"],
  "based_on_findings": ["finding-<id1>", "finding-<id2>"]
}
```

Поля:
- `content` — свободный текст модели. Два назначения в одном: (1) целостная картина здоровья пользователя — что известно, ключевые выводы, критические данные (аллергии, противопоказания), текущая картина здоровья и питания; (2) навигационная карта памяти — какие есть findings по каким темам, какие факты критичны, что модель должна «помнить» при входе в контекст.
- `based_on_facts` — machine-readable ссылки на все факты, учтённые при написании. Заполняется субагентом при обновлении.
- `based_on_findings` — ссылки на все findings, учтённые при написании.
- `foundation_changed` (в `active.json`) — флаг, выставляемый ядром при `correct_user_reported_fact`, если исправленный факт присутствует в `based_on_facts` активного мастер-описания. Модель при следующем `read_master_description` видит флаг и решает, требуется ли переписать мастер-описание.

При `rewrite_master_description` старая версия сохраняется (не удаляется), новая становится активной через обновление `active.json`, флаг `foundation_changed` сбрасывается в `false`.

**Протокол обновления (субагент):**

Модель вызывает `update_master_description`. Ядро запускает субагента (отдельный LLM-вызов с изолированным контекстом). Субагент выполняет строго последовательно:

1. **Загружает текущее master-описание** через `read_master_description` (если master отсутствует — начинает с пустым контекстом).
2. **Загружает все facts.** Пагинирует `list_facts` + `read_fact` по каждому факту, пока не кончатся. Без исключений — все imported и все user-reported.
3. **Загружает все findings.** Пагинирует `list_findings` + `read_finding` по каждому finding, пока не кончатся. Без исключений.
4. **Проверяет консистентность:** нет ли фактов без findings, нет ли findings с `foundation_changed=true` без разрешения, нет ли расхождений между фактами и текущим мастер-описанием.
5. **Вызывает `rewrite_master_description(content)`** — тул, принимающий полный текст нового мастер-описания (≤50 000 токенов) с заполненными `based_on_facts` и `based_on_findings`. Ядро сохраняет старую версию, обновляет `active.json`, коммитит.
6. **Возвращает результат модели.**

Это один пасс. Контекста субагента должно хватить: 50k (master) + все facts (каждый ≤1k, с disclaimer'ом) + все findings (каждый ≤1k). Для масштаба персонального ассистента (сотни фактов и findings) укладывается в типичное контекстное окно. При экстремальном росте хранилища протокол остаётся тем же — субагент пагинирует.

**Периодичность:** модель вызывает `update_master_description` при housekeeping (см. Фазу 4). Вне housekeeping — по усмотрению модели, если накопилось значимое количество незафиксированных findings.

### Conversational Preferences (предпочтения по общению)

Отдельный файл. ≤ 1024 токена. Модель переписывает целиком.

```
data/conversational-preferences/
├── current.json  # активный файл
└── backup.json   # одна предыдущая версия
```

Структура `current.json`:

```json
{
  "updated_at": "<системная дата>",
  "content": "<текст модели, ≤1024 токена>"
}
```

Backup ровно один. При каждом `rewrite` текущий `current.json` становится `backup.json`, новое содержимое пишется в `current.json`. Старый backup теряется безвозвратно. `restore` меняет местами `current.json` ↔ `backup.json`.

## Тулинг

Все write-тулы проходят трёхуровневую защиту: валидация в памяти → atomic rename (write(.tmp) → fsync → rename) → git commit.

### Read-тулы (7)

| Тул | Параметры | Возвращает |
|-----|-----------|------------|
| `list_facts` | `type?`: `"imported"` \| `"user_reported"`, `offset`: u32, `limit`: u32 | `[{id, type, title, created_at, version, findings_count}]` |
| `read_fact` | `fact_id`: string | Полный факт: текущая версия (content + disclaimer для user-reported) + индекс версий `[{version, created_at, reason}]` + список findings |
| `list_findings` | `offset`: u32, `limit`: u32 | `[{id, title, created_at, status, foundation_changed, based_on_fact_ids}]` |
| `read_finding` | `finding_id`: string | Полный finding (content + based_on факты + статус + foundation_changed) |
| `read_master_description` | — | Текущее мастер-описание + флаг `foundation_changed` |
| `read_conversational_preferences` | — | Текущий файл предпочтений |

**Унификация list/read тулов для facts:** в ранних требованиях (секция «Тулинг для user-reported facts») предполагались раздельные `list_user_reported_facts` / `list_imported_facts` и `read_user_reported_fact` / `read_imported_fact`. Унификация через параметр `type?` сокращает количество тулов без потери семантики: обе категории фактов имеют одинаковую структуру в индексном представлении (ID, type, title, created_at, findings_count), различаясь только disclaimer при полном чтении. Модель фильтрует по `type` когда нужно, иначе получает общий список.

**`list_facts`:** title для user-reported — первые ~80 символов content. Для imported — название исследования/анализа. `findings_count` — количество findings с обратной ссылкой на факт. `version` — текущая версия факта.

**`list_findings`:** title — первые ~80 символов content. `foundation_changed` — критический флаг: модель сразу видит, какие findings требуют пересмотра.

**`read_finding`:** ядро отдаёт finding.json целиком вместе с содержимым based_on фактов.

### Write-тулы (9)

| Тул | Параметры | Инварианты ядра |
|-----|-----------|-----------------|
| `create_user_reported_fact` | `content`: string, `presumed_date?`: string | Добавляет disclaimer с текущей датой, проверяет суммарный размер (disclaimer + content модели) ≤1024 токена. При превышении — ошибка с указанием текущего размера и лимита. `presumed_date` — ISO 8601 или свободный текст со слов пользователя («прошлым летом», «в 2020 году») |
| `correct_user_reported_fact` | `fact_id`: string, `content`: string, `reason`: string, `presumed_date?`: string | Сохраняет старую версию, создаёт новую. Выставляет `foundation_changed=true` на всех findings с based_on на этот факт. Если факт есть в `based_on_facts` активного мастер-описания — выставляет `foundation_changed=true` в `active.json`. `presumed_date` — опционально, при отсутствии сохраняется предыдущее значение |
| `create_finding` | `content`: string, `based_on_fact_ids`: string[], `reason`: string | Проверяет ≤1024 токена, валидирует все факты существуют, создаёт finding, обновляет обратные ссылки (дописывает finding_id в fact.findings). Атомарно |
| `resolve_finding_status` | `finding_id`: string, `status`: `"superseded"` \| `"reaffirmed"`, `reason`: string | `superseded` — finding.status = "superseded". `reaffirmed` — сбрасывает `foundation_changed=false`. Ядро отклоняет `reaffirmed` если `foundation_changed != true` |
| `rewrite_master_description` | `content`: string, `based_on_facts`: string[], `based_on_findings`: string[] | Прямая запись мастер-описания (≤50 000 токенов). Старая версия сохраняется, новая становится активной через обновление `active.json`. Может вызываться моделью напрямую для быстрого обновления без полного субагент-пасса |
| `update_master_description` | — | Запускает субагента (отдельный LLM-вызов). Субагент выполняет протокол: read_master_description → все facts → все findings → проверка консистентности → `rewrite_master_description(content)`. Параметров нет — субагент сам обходит все данные |
| `rewrite_conversational_preferences` | `content`: string | Проверяет ≤1024 токена, current → backup, новый → current |
| `restore_conversational_preferences` | — | Меняет current ↔ backup местами (повторный вызов — откат обратно) |

**Отказы ядра (возвращается ошибка, запись не происходит):**
- Контент превышает токен-лимит → ошибка с указанием текущего размера и лимита
- `based_on_fact_ids` содержит несуществующий ID → ошибка с указанием каких именно
- `fact_id` не существует в `correct_user_reported_fact` или `resolve_finding_status` → ошибка
- `finding_id` не существует в `resolve_finding_status` → ошибка
- `status` не `"superseded"` и не `"reaffirmed"` → ошибка валидации

**Отказы по инвариантам:**
- `resolve_finding_status(reaffirmed)` для finding без `foundation_changed=true` → ошибка: нечего reaffirm
- `resolve_finding_status(superseded)` для уже superseded finding → ошибка: уже в этом статусе

### Сознательно не включены в MVP

| Не включено | Причина |
|-------------|---------|
| `delete_fact` / `delete_finding` | Удаление — только через UI, инициатива пользователя (см. принцип версионирования) |
| `search_facts` / `search_findings` | Плоский индекс + пагинация достаточен для масштаба персонального ассистента |
| `batch_create_findings` | Атомарность в рамках одного finding. Пакет создаёт риск частичного отказа и рассогласования |
| `link_fact_to_finding` / `unlink` | Ссылки задаются при создании finding и never modified |
| `update_imported_fact` | Импорт — отдельный pipeline, не через модель |
| Тулы для `topics/` | Topics как навигационный индекс над историей диалога — отдельная подсистема, не часть MVP памяти |
| `check_discrepancies` (как отдельный тул) | Консистентность проверяется субагентом внутри `update_master_description` (см. Фазу 5). Отдельный тул не нужен |

## Фазы реализации

### Фаза 1: Типы и storage-слой (без LLM-тулинга)

**Модуль:** `src-tauri/src/memory/` (новый)

- `mod.rs` — pub use модулей
- `types.rs` — структуры: `UserReportedFact`, `ImportedFact`, `Finding`, `MasterDescription`, `ConversationalPreferences`, `FactVersion`, перечисления (FactType, FindingStatus)
- `facts.rs` — CRUD для facts: create, read (по ID), list (с пагинацией), correct (сохранение истории версий). Только user-reported; imported facts — read-only заглушка под будущий import pipeline
- `findings.rs` — CRUD для findings: create (с валидацией based_on ссылок), read (по ID), list (с пагинацией и статусными флагами), resolve_status
- `master_description.rs` — read (текущее), rewrite (с сохранением версий)
- `master_description.rs` — read (текущее), update (запуск субагента)
- `conversational_preferences.rs` — read, rewrite (с backup), restore
- `storage.rs` — общие хелперы: atomic_write (tmp → fsync → rename), подсчёт токенов (tiktoken-rs или оценка), валидация токен-лимитов

**Тесты:** unit-тесты на каждый CRUD. Инварианты: atomic write не повреждает файл, переполнение токенов детектится, based_on ссылки валидируются.

### Фаза 2: Git commit automation

**Модуль:** `src-tauri/src/git.rs` (новый) или расширение существующего

- `auto_commit(message, paths)` — git add + git commit с указанным сообщением
- Интеграция в write-тулы: каждый успешный write → auto_commit с описательным message (тип операции + ID сущности)

### Фаза 3: Регистрация тулов в ToolRegistry

**Модуль:** `src-tauri/src/tools/memory.rs` (новый)

- 16 тулов (7 read + 9 write) как функции с сигнатурой, совместимой с существующим `ToolRegistry`
- Каждый тул: парсинг аргументов → валидация → вызов storage-слоя → atomic write → git commit (для write) → сериализация ответа
- Интеграция в `src-tauri/src/tools/mod.rs`

**Тесты:** интеграционные тесты на каждый тул — создание, чтение, коррекция, флаги foundation_changed (findings и master description), backup/restore предпочтений.

### Фаза 4: Интеграция с ChatSession и контекстом

- Автосохранение диалога в `data/history/` (append-only JSONL с fsync)
- Инжекция memory-тулов в системный промпт модели

**Содержание описаний memory-тулов (инжектится в системный промпт):**

- **Назначение подсистемы памяти:** why it exists — превратить одноразовый диалог в накапливаемые, структурированные знания о пользователе, переживающие очистку контекста.
- **User-Reported Facts vs. Imported Facts:** эпистемический статус. User-reported — суждение пользователя, может быть неточно/ошибочно/ложно. Imported — медицинский документ с provenance, безусловный приоритет. Модель должна понимать разницу и учитывать её при создании findings.
- **Критерии фиксации факта:** когда вызывать `create_user_reported_fact`. Факт достоин фиксации если он: (а) сообщён пользователем как объективное сведение о себе, (б) потенциально переиспользуем в будущих выводах, (в) не является тривиальной репликой в потоке диалога. Модель не должна фиксировать каждое высказывание пользователя — только факты.
- **Семантика `foundation_changed`:** что значит флаг на finding и master description. Модель обязана явно решить по каждому finding с флагом (supersede или reaffirm) и по мастер-описанию с флагом (переписать или игнорировать). Необработанный флаг — detected inconsistency, будет показан при следующей загрузке контекста.
- **Семантика master-описания:** назначение — целостная картина здоровья + навигационное оглавление памяти, всегда в контексте. Отвечает на вопросы «какова картина здоровья пользователя» и «что у нас есть в памяти и куда смотреть». Обновляется через `update_master_description` — субагент за один пасс обходит все facts и все findings, проверяет консистентность и переписывает мастер-описание. Модель вызывает этот тул при housekeeping; вне housekeeping — по усмотрению.
- **Семантика rewrite тулов:** `rewrite_conversational_preferences` — полная замена, backup сохраняется один раз, restore однократный. `rewrite_master_description` — полная замена, все версии сохраняются, активна последняя.

**Мониторинг заполнения контекста (инжектится в системный промпт):**

Модель обязана отслеживать заполнение контекстного окна. Критерии:
- При достижении ~70% контекстного окна модель предупреждает пользователя: контекст заполняется, часть истории скоро будет вытеснена.
- При достижении ~85% модель обязана инициировать housekeeping до продолжения предметного диалога.
- При любом уровне заполнения модель вправе инициировать housekeeping досрочно, если накопилось значимое количество незафиксированных выводов.

Housekeeping не прерывает диалог — модель выполняет его в рамках того же conversation turn, вызывая write-тулы для сохранения знаний перед очисткой контекста.

**Инструкция фиксировать findings (инжектится в системный промпт):**

Модель обязана фиксировать finding немедленно по мере его вывода в диалоге, не откладывая до housekeeping. Критерий: любой нетривиальный вывод из фактов, который может быть переиспользован в будущем, должен быть записан через `create_finding` сразу. Housekeeping не должен быть моментом, когда модель судорожно вспоминает все выводы за сессию — к моменту housekeeping все значимые findings уже записаны.

**Процедура housekeeping для новой архитектуры:**

В текущей архитектуре (без topics) housekeeping при срабатывании триггера:
1. **Вызвать `update_master_description`** — субагент пересобирает мастер-описание по всем facts + findings. Это основной шаг, заменяющий умную балансировку дерева тупым полным обходом.
2. **При необходимости обновить master description напрямую** — если модель хочет быстро обновить мастер-описание без полного субагент-пасса, вызывает `rewrite_master_description`.
3. **Обновить conversational preferences** — если в диалоге проявились новые паттерны общения, предпочтения, триггеры.

### Фаза 5: Master Description (навигационный слой)

**Модуль:** `src-tauri/src/memory/master_description.rs` (новый)

- `master_description.rs` — read (текущее), update (запуск субагента), хранение версий
- **Субагент:** `update_master_description` — отдельный LLM-вызов с изолированным контекстом:
  1. Загружает текущее master-описание (если есть)
  2. Пагинирует `list_facts` + `read_fact` по всем фактам (обеих категорий)
  3. Пагинирует `list_findings` + `read_finding` по всем findings
  4. Проверяет консистентность: факты без findings, `foundation_changed` без разрешения, расхождения с текущим мастер-описанием
  5. Вызывает `rewrite_master_description(content)` с заполненными `based_on_facts` и `based_on_findings`
  7. Возвращает результат модели
- **Интеграция в housekeeping:** `update_master_description` становится основным шагом housekeeping (Фаза 4)
- **Интеграция в системный промпт:** модель получает описание назначения master-описания — навигационное оглавление памяти, всегда в контексте

**Отличия от первоначальной древовидной модели:**
- Нет дерева, нет корневой ноды, нет метрики важности, нет автоматической балансировки
- Нет частичной загрузки (верх в контексте, остальное по ссылкам). Master-описание всегда полное — оно само по себе компактно (≤50k токенов) и всегда помещается в контекст
- Нет политики забывания/вытеснения. Все facts и findings равнодоступны через честную пагинацию. Модель сама решает, что релевантно текущей задаче
- Критические неснижаемые данные (аллергии, противопоказания) — не структурный инвариант, а инструкция модели: они должны быть явно выделены в master-описании

## Что не входит в данный план

- Импорт медицинских документов (pipeline для imported facts)
- Древовидная структура user-map (заменена на Master Description как навигационный слой — реализован)
- Topics (индекс над историей диалога)
- Режим расследования (investigation mode)
- Шифрование данных на диске
- UI для просмотра/редактирования памяти
- Миграция `parameters/` → `facts/imported/`: существующая директория `data/parameters/` (определена в исходной структуре `data/`) остаётся как есть. `facts/imported/` — целевая структура для новых imported facts. Миграция не требуется в MVP (imported facts — future, pipeline импорта не реализован)
